# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

`unshittify` is a Claude Code **plugin marketplace**: a `.claude-plugin/marketplace.json` listing eight plugins under `plugins/`, each a self-contained bundle of skills (`skills/<name>/SKILL.md`) and subagents (`agents/<name>.md`). Everything under `plugins/` is a JSON manifest or a Markdown prompt that the Claude Code harness loads directly — no application code and no build step. It is checked by `tests/plugins/validate-plugins.sh` (below) rather than by a compiler. `hooks/` is real bash code with its own test suite.

Plugins:
- `local` — manage project-local settings (`.claude/settings.local.json`): theme, model, per-project plugin enable/disable, a settings-doctor audit.
- `global` — the settings-doctor audit again, scoped to `~/.claude/settings.json`, plus a separate slash-command-only skill that repairs missing hook wiring.
- `git` — commit-message drafting and git-history exploration agents/skills.
- `meta` — skills for authoring new skills and agents *for this repository*, encoding this repo's own house style.
- `communication` — reviews drafted prose against this repo's style bar before it reaches the user.
- `racket` — a large, mostly independent set of reference skills for the Racket language (classes, contracts, macros, GUI, testing, packaging, etc.), each with a `SKILL.md` + `reference.md` pair.
- `development` — language-agnostic development discipline: the `make-changing-easy` precondition, and the TDD, NST (Normalized Systems Theory), property-test, and efficiency review post-conditions. `hooks/enforce-code-review.sh` requires these four reviews by name, so this plugin is not optional decoration — removing or renaming one of its skills or agents breaks that hook.
- `cxx` — C++ work: sanitizer builds, structural search with clang-query, and this repo's C++ editing idioms.

## Commands

There is nothing to compile under `plugins/`, but it is not unchecked:

- **Check everything**: `tests/run_tests.sh` — `shellcheck` over the shell code, then each `tests/<name>/run_tests.sh`, then the validator against this repository. `.github/workflows/tests.yml` runs this same script on every push and pull request, so the local answer and the continuous-integration answer come from one command.
- **Validate every plugin file**: `tests/plugins/validate-plugins.sh` — run this after ANY edit under `plugins/`. It checks the whole tree and prints `path:line: message` per violation. See "The `tests/plugins/` validator" below for what it catches and why each check exists.
- **List installed plugins / their enabled state**: `claude plugin list --json`.
- **Exercise a skill or agent manually**: install/enable the plugin locally, then invoke its slash command (e.g. `/local:check-settings`) or trigger its agent by description in a live session — there is no offline harness for this.
- **Publish an edit to a running session**: `scripts/update-install.sh` — refreshes the marketplace, republishes every plugin the manifest names, then verifies each installed snapshot against the tree and exits non-zero if any is stale. `--dry-run` prints the commands, `--verify-only` reports staleness without changing anything, `--force` reinstalls everything. It reinstalls rather than updates a plugin whose version did not move, because `claude plugin update` is keyed on the version string and reports success while copying nothing. Editing a file under `plugins/` alone changes nothing a session sees — see "Installing copies the tree" below. Restart, or run `/reload-plugins`, afterwards.

For `hooks/`, see the next section.

## The `hooks/` directory

`hooks/` holds personal Claude Code hook scripts (bash) — not a plugin, and not loaded by the marketplace manifest. They are wired into `~/.claude/settings.json` by absolute path, so they take effect globally, in every project, regardless of which repository is the current working directory:

- `hooks/enforce-prose-review.sh` (`Stop`) — blocks ending a turn if the final assistant message is substantial prose and the `communication:prose-reviewer` agent was not invoked on it this turn. "Substantial" is a word count taken after fenced blocks and inline code spans are removed, so a reply that is mostly a diff does not trip it. A stdin payload it cannot parse leaves it silent, since without the payload there is no message to measure; the code-review hook blocks on that same payload, so the turn still does not end unjudged.
- `hooks/enforce-code-review.sh` (`Stop`) — blocks ending a turn if a file was written or edited this turn but the required reviews (TDD (test-driven development), NST (Normalized Systems Theory), property-tests, efficiency — each satisfiable via its skill or its matching subagent) were not all invoked since the user's last message. "Edited" covers three routes, not just the `Edit` tool: a `Bash` command matching `BASH_WRITE_PATTERNS`, and delegation to any subagent not named in `READ_ONLY_AGENTS`, both count. The auto mode of the harness tells the model to prefer `sed` and heredocs over `Edit`, so watching tool names alone left the gate open on the path the model is actively told to take. `READ_ONLY_AGENTS` is a judgement about what each listed agent is instructed to do, not a fact derived from its `tools:` line — every entry defined in this repository holds a tool that writes: `Bash` for all of them but `communication:prose-reviewer`, which holds `Edit` (and no `Bash`) and is listed anyway, because `enforce-prose-review.sh` mandates that agent and counting the mandated call as a possible edit left the two hooks with no move that satisfies both. Read an agent's whole body, not its tools line, before adding a name. A stdin payload this hook cannot parse blocks rather than exiting nonzero: the payload is what names the transcript, so without it there is no evidence either way, and every exit status but 0 and 2 reads to the harness as a non-blocking error.
- `hooks/confirm-git-commit-push.sh` (`PreToolUse`, matcher `Bash`) — asks for confirmation before a `git commit` or `git push` runs, since those require an explicit instruction in the current turn. A `git commit` is denied outright until `communication:prose-reviewer` has run in the same turn. The gate tokenises the command rather than pattern-matching it, so it reads the subcommand as the first non-option word after a `git` command word: `git help commit` and `git log --grep commit` are not gated, while `bash -c "git commit -m x"`, `git "commit"` and `git -C "/a;b" commit` are.
- `hooks/lib/transcript.sh` — sourced by all three, never executed alone. It is the single place that knows the raw JSONL transcript schema: where a turn begins, how `tool_use` events are shaped, and what counts as an exact agent-name match. Change a schema assumption here, not in a hook. It also carries `turn_requests_brevity`, the one piece of shared policy: both `Stop` hooks stand down for a turn whose genuine user prompt opens with "Briefly" or "briefly", and the rule lives beside the schema helpers so the two gates cannot drift apart on which turns are exempt. Only positive evidence opts out — a marker-fallback boundary or an unreadable prompt exempts nothing.

The turn boundary in `transcript.sh` deserves particular care. The harness records several of its OWN messages in the user role with plain string content — a completion notification for an asynchronous subagent, a slash-command marker, local command output — and each one that counts as a boundary discards the evidence of everything the assistant did earlier in the same turn. The task-notification case broke a real guarantee: it is written *after* the `Agent` call that spawned the subagent, so `enforce-prose-review.sh` could never see a review it had just demanded, and every review in this harness is delegated that way. `find_turn_start_line` now rejects harness-authored messages by `origin.kind` and by content shape. Both rules only ever move the boundary *earlier*, which is the safe direction: an earlier boundary can only make a hook see more of the turn, never less.

That safety is now pinned by tests rather than only argued here. `tests/hooks/transcript-lib.bats` requires one boundary verdict per transcript record (a prompt carrying several text blocks must not shift every later line number), a boundary that never lands past the transcript's last line, a malformed line that does not discard the events around it, and a last-prompt marker matched as a record rather than as quoted text inside a tool result. If you change the boundary logic, those tests — not the prose above — are what will tell you whether the direction still holds.

All the scripts must pass `shellcheck` cleanly. `tests/run_tests.sh` runs it first, over the hooks, the validator and the runners themselves, so there is no separate invocation to remember after editing one. They have a test suite under `tests/hooks/`, using `bats` (bats-core) rather than any custom harness — run the whole suite with `tests/hooks/run_tests.sh`. Follow strict TDD when changing this logic: these scripts encode real decision functions (e.g. `enforce-code-review.sh`'s missing-reviews computation has stated laws — monotonicity, order-invariance, duplicate-insensitivity — each pinned by a test in `tests/hooks/enforce-code-review.bats`), not incidental scripting, so a behavior change belongs behind a new failing test first.

## The `tests/plugins/` validator

`tests/plugins/validate-plugins.sh` is the only thing that checks the Markdown and JSON that are the actual product. Run it after any edit under `plugins/`:

```
tests/plugins/validate-plugins.sh          # check the repository
tests/plugins/run_tests.sh                 # check the validator itself (bats)
```

It prints one `path:line: message` per violation and exits non-zero if there were any. Every check exists because the corresponding defect had already shipped:

| Check | What shipped broken |
|-------|---------------------|
| unquoted frontmatter scalar containing ` #` | four Racket descriptions truncated mid-sentence by a YAML comment |
| a sibling file the `SKILL.md` never names | thirteen `reference.md` files nothing instructed the model to open |
| unknown tool in `allowed-tools` / `tools` | `Task(...)` left in a skill after the harness renamed that tool to `Agent` |
| the two manifests disagreeing | see commit `665f550` |
| agent missing `name`/`description`/`tools`/`model`, a `model` outside `KNOWN_MODELS`, or a name not matching its filename | the rule held only by convention |
| skill missing `description` | a skill with no description can never trigger |
| a tool list written as an indented YAML block sequence | the entries never reached the tool check, so an unknown tool spelled that way passed |
| a frontmatter key the harness does not read, or one written twice | `tools:` where the harness reads `allowed-tools:` grants no tools and says nothing; a repeated key silently took the last value |
| a root with no `plugins/` directory, or holding no skill and no agent | a mistyped path validated an empty set and printed `plugins: clean.` |
| an argument-scoped tool in an agent's `tools` | the known-name check strips the argument off first, so the bare-names rule for agents held only in the meta plugin's prose |

The frontmatter now has one reader. `read_markdown` publishes the keys, their raw values, their line numbers, the duplicates and the body, and no check parses a line of its own. Two parsers over one input is how the truncation check came to disagree with the loader about leading whitespace and flag a correctly quoted description as truncated whenever it was indented.

Add a check the same way you would add a hook behaviour: a failing test in `tests/plugins/validate-plugins.bats` first, built on a throwaway fixture tree rather than on live repository content, then the check.

## Architecture and conventions specific to this repo

- **Two manifests state each plugin's description.** Each plugin has its own `plugins/<name>/.claude-plugin/plugin.json`, and `.claude-plugin/marketplace.json` at the repo root duplicates that description in its `plugins[]` entry. They drifted once already — see commit `665f550`. `tests/plugins/validate-plugins.sh` now compares them, and also flags a plugin directory missing from the marketplace manifest. When a plugin's scope or description changes, update both files and run the validator.
- **Installing copies the tree, into a directory named after the version.** `claude plugin install` writes a snapshot to `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, and that snapshot — never the working tree — is what a session loads. So a content change that leaves `version` alone reuses the same directory, and nothing downstream can tell the copy is stale. That has already happened: `development` gained a whole agent (`efficiency-reviewer.md`) in commit `b27d40b` and a `model` field on every agent in `cfa0f0a`, all at version `0.1.0`, leaving the installed copy with four agents where the tree has five. Bump `version` in `plugins/<name>/.claude-plugin/plugin.json` in the same change that edits the plugin — minor for an added or changed skill or agent — then reinstall as described under "Commands".
- **The skill/agent distinction, and how to author each, is documented in-repo**: `plugins/meta/skills/write-skill/SKILL.md` and `plugins/meta/skills/write-agent/SKILL.md` are the canonical rules for frontmatter fields, tool scoping, and body structure for any new `SKILL.md` or agent file added anywhere in this repository. Read those before adding or editing a skill/agent rather than inferring conventions from a single example, since some plugins predate parts of that style guide.
- **The meta plugin states each authoring rule twice, and nothing keeps the two copies together.** `plugins/meta/skills/write-agent/SKILL.md` and `plugins/meta/agents/agent-writer.md` both carry the house rules for agent frontmatter (and likewise `write-skill/SKILL.md` with `skill-writer.md`), because one is used directly and the other when the work is delegated to a subagent. Changing a rule in the skill without changing it in the matching agent leaves the delegated path scaffolding files that violate the rule the skill just introduced — this happened when the `model` field became required. Update both.
- **Every agent names its model.** Each `plugins/*/agents/*.md` carries a `model` field: `haiku` for mechanical work, `sonnet` for judgment. None inherit the caller's model, so an agent's cost and capability do not change with the session's model. `tests/plugins/validate-plugins.sh` enforces this.
- **Skills in this repo are single-file.** No plugin uses a `skills/<name>/references/`, `scripts/`, or `assets/` subdirectory — everything lives in one `SKILL.md`. The `racket` plugin's `reference.md` alongside each `SKILL.md` is the one exception, kept because those files are large lookup tables, not instructions. **A sibling file is only reachable if the `SKILL.md` body names it** — nothing else tells the model to open it. Thirteen Racket skills once shipped a `reference.md` no `SKILL.md` mentioned, stranding roughly 1,600 lines. The validator now requires the citation, rejects a citation that resolves to no file, and rejects a subdirectory inside a skill.
- **Quote any frontmatter value containing a space followed by `#`.** YAML ends an unquoted scalar there, so a description mentioning a Racket `#:keyword` reaches the harness cut in half — usually losing the `Use when...` clause that makes the skill triggerable at all, while the file on disk still reads correctly. Four Racket skill descriptions shipped this way. The validator now rejects it.
- **The `local` and `global` plugins are parallel by design, not by accident.** `plugins/local/agents/settings-doctor.md` and `plugins/global/agents/settings-doctor.md` (and their matching `check-settings` skills) run mostly the same checks against different files (`.claude/settings.local.json` vs `~/.claude/settings.json`), worded identically wherever they overlap. Each keeps what only means anything in its own scope: `local` alone asks whether a rule duplicates one already granted higher up and whether the file is git-ignored, `global` alone asks whether a marketplace's hook scripts are wired into `hooks`. The two also describe settings precedence differently, because the same file sits at opposite ends of it. When fixing a bug in one settings-doctor's check logic, check whether the same bug exists in the other — they are not shared via any common file, so nothing keeps them in sync automatically.
- **Commit messages follow a fixed template** (emoji, `[module] <new state, not action taken>` subject, Problem/Solution bullets, closing haiku) — this is codified in `plugins/git/skills/commit-message/SKILL.md` and the `git:commit-writer` agent. Always invoke that skill (or the agent, when delegating to a subagent) for every commit in this repository — never write a commit message without the template — unless the user has explicitly said not to use the template. **The agent drafts only; it never commits.** It holds no tool that can invoke a subagent, so it cannot satisfy `confirm-git-commit-push.sh`'s prose-review gate; its caller runs the reviewer and the commit. The skill is deliberately set up to auto-trigger on any explicit commit request, not only on the literal `/git:commit-message` command, so the format stays consistent with the existing log.
- **`.org` files at the repo root are intentionally untracked.** `BadProseExamples.org` (the growing catalogue of prose failures that `review-prose/SKILL.md` and `prose-reviewer.md` each read at the start of a review) and `Review.org` are excluded by the user's global `~/.gitignore` (`*.org`), not this repo's own `.gitignore` (which is empty). If `BadProseExamples.org` is missing on a fresh checkout, that is expected — both files instruct the reviewer to fall back to the curated examples they carry inline, and neither to report its absence nor to create it; do not try to force it into the repository. The two copies of that instruction drift the same way the meta plugin's do: change one, change the other.
