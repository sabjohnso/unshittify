# CLAUDE.md

This file gives guidance to Claude Code (claude.ai/code) for work in this repository.

## What this repository is

`unshittify` is a Claude Code **plugin marketplace**. A `.claude-plugin/marketplace.json` lists eight plugins under `plugins/`. Each plugin is a self-contained bundle of skills (`skills/<name>/SKILL.md`) and subagents (`agents/<name>.md`). Everything under `plugins/` is a JSON manifest or a Markdown prompt that the Claude Code harness loads directly. There is no application code and no build step. `tests/plugins/validate-plugins.sh` (below) checks it. No compiler does. `hooks/` is real bash code with its own test suite.

Plugins:
- `local` manages project-local settings (`.claude/settings.local.json`): the theme, the model, the plugins that are enabled per project, and a settings-doctor audit.
- `global` runs the settings-doctor audit again, with `~/.claude/settings.json` as its scope. A separate slash-command-only skill repairs missing hook wiring.
- `git` holds the agents and the skills for a commit-message draft and for an exploration of the git history.
- `meta` holds the skills that write new skills and agents *for this repository*. They encode the house style of this repository.
- `communication` holds the condensed rules of Simplified Technical English (ASD-STE100) in its `simplified-technical-english` skill. It reviews prose against STE and the house style through `review-prose` and the `prose-reviewer` agent, and it aligns markdown tables. `hooks/enforce-prose-review.sh` mandates that agent on every substantial reply.
- `racket` is a large set of reference skills for the Racket language (classes, contracts, macros, GUI, testing, packaging, and more). The skills are mostly independent of each other. Each one is a `SKILL.md` and `reference.md` pair.
- `development` holds language-agnostic development discipline: the `make-changing-easy` precondition, and the TDD (test-driven development), NST (Normalized Systems Theory), property-test, and efficiency review postconditions. `hooks/enforce-code-review.sh` requires these four reviews by name. So this plugin is not optional decoration. A removal or a rename of one of its skills or agents breaks that hook.
- `cxx` holds the C++ work: sanitizer builds, structural search with clang-query, and the C++ editing idioms of this repository.

## Commands

There is nothing to compile under `plugins/`, but the tree is not unchecked:

- **Check everything**: `tests/run_tests.sh`. It runs `shellcheck` over the shell code, then each `tests/<name>/run_tests.sh`, then the validator against this repository. `.github/workflows/tests.yml` runs this same script on every push and pull request. So the local answer and the continuous-integration answer come from one command.
- **Validate every plugin file**: `tests/plugins/validate-plugins.sh`. Run it after EACH edit under `plugins/`. It checks the whole tree and prints one `path:line: message` per violation. See "The `tests/plugins/` validator" below for what it catches and why each check exists.
- **List the installed plugins and their enabled state**: `claude plugin list --json`.
- **Run a skill or an agent by hand**: install and enable the plugin locally. Then call its slash command (for example `/local:check-settings`), or trigger its agent by description in a live session. There is no offline harness for this.
- **Publish an edit to a live session**: `scripts/update-install.sh`. It refreshes the marketplace, publishes every plugin that the manifest names again, then verifies each installed snapshot against the tree. It exits with a nonzero status if a snapshot is stale. `--dry-run` prints the commands. `--verify-only` reports stale snapshots and changes nothing. `--force` reinstalls every plugin. The script reinstalls a plugin whose version did not move, and it does not update it, because `claude plugin update` keys on the version string and reports success while it copies nothing. An edit of a file under `plugins/` alone changes nothing that a session sees. See "An install copies the tree" below. Afterwards, restart the session or run `/reload-plugins`.

For `hooks/`, see the next section.

## The `hooks/` directory

`hooks/` holds personal Claude Code hook scripts (bash). It is not a plugin, and the marketplace manifest does not load it. The scripts are wired into `~/.claude/settings.json` by absolute path. So they apply globally, in every project, whatever repository is the current working directory:

- `hooks/enforce-prose-review.sh` (`Stop`) blocks the end of a turn if the final assistant message is substantial prose and the `communication:prose-reviewer` agent did not run on it this turn. That agent applies the Simplified Technical English checks first, then the house-style checklist. "Substantial" is a word count taken after the removal of the fenced blocks and the inline code spans. So a reply that is mostly a diff does not trip it. A stdin payload that the hook cannot parse leaves it silent, because without the payload there is no message to measure. The code-review hook blocks on that same payload, so the turn still does not end with no judgement.
- `hooks/enforce-code-review.sh` (`Stop`) blocks the end of a turn if a file was written or edited this turn and not all of the required reviews ran after the last message from the user. The required reviews are TDD, NST, property tests, and efficiency. A skill or its matching subagent satisfies each one. "Edited" covers three routes, not only the `Edit` tool. An `Edit`, `Write`, or `NotebookEdit` call does not count when `EDIT_EXEMPT_PATHS` matches its file: a path under `/tmp` or `/var/tmp`, or a memory note under `~/.claude/projects/<project>/memory/`. Those files are not code, and the scratchpad drafts of a reply caused a block on every turn. A `Bash` command that matches `BASH_WRITE_PATTERNS` counts, and a delegation to a subagent that is not in `READ_ONLY_AGENTS` counts. The auto mode of the harness tells the model to prefer `sed` and heredocs over `Edit`. So a watch on tool names alone left the gate open on the path that the model is told to take. `READ_ONLY_AGENTS` is a judgement about what each listed agent is told to do. It is not a fact derived from the `tools:` line of the agent. Every entry defined in this repository holds a tool that writes: `Bash` for all of them but `communication:prose-reviewer`. That agent holds `Edit` (and no `Bash`) and is in the list anyway, because `enforce-prose-review.sh` mandates it. When the mandated call counted as a possible edit, the two hooks had no move that satisfied both. Read the whole body of an agent, not its tools line, before you add a name. A stdin payload that this hook cannot parse blocks. It does not exit with a nonzero status. The payload names the transcript, so without it there is no evidence either way, and the harness reads every exit status but 0 and 2 as a non-blocking error.
- `hooks/confirm-git-commit-push.sh` (`PreToolUse`, matcher `Bash`) asks for confirmation before a `git commit` or a `git push` runs, because those need an explicit instruction in the current turn. It denies a `git commit` until `communication:prose-reviewer` has run in the same turn. The gate tokenizes the command. It does not match a pattern. So it reads the subcommand as the first non-option word after a `git` command word. `git help commit` and `git log --grep commit` are not gated. `bash -c "git commit -m x"`, `git "commit"`, and `git -C "/a;b" commit` are gated.
- `hooks/lib/transcript.sh` is sourced by all three hooks. Nothing executes it alone. It is the single place that knows the raw JSONL transcript schema: where a turn starts, the shape of a `tool_use` event, and what counts as an exact agent-name match. Change a schema assumption here, not in a hook. It also holds `turn_requests_brevity`, the one piece of shared policy. Both `Stop` hooks stand down for a turn whose genuine user prompt opens with "Briefly" or "briefly". The rule is beside the schema helpers, so the two gates cannot drift apart on which turns are exempt. Only positive evidence opts out. A marker-fallback boundary or an unreadable prompt exempts nothing.

The turn boundary in `transcript.sh` needs special care. The harness records several of its OWN messages in the user role with plain string content: a completion notification for an asynchronous subagent, a slash-command marker, and local command output. Each one that counts as a boundary discards the evidence of all that the assistant did earlier in the same turn. The task-notification case broke a real guarantee. The harness writes it *after* the `Agent` call that started the subagent. So `enforce-prose-review.sh` could never see a review that it had just demanded, and every review in this harness is delegated that way. `find_turn_start_line` now rejects messages that the harness wrote, by `origin.kind` and by content shape. Both rules only move the boundary *earlier*, and that is the safe direction. An earlier boundary can only make a hook see more of the turn, never less.

Tests now pin that safety. This file does not only argue it. `tests/hooks/transcript-lib.bats` requires one boundary verdict per transcript record (a prompt with several text blocks must not move every later line number), a boundary that never lands after the last line of the transcript, a malformed line that does not discard the events around it, and a last-prompt marker that matches as a record and not as quoted text inside a tool result. If you change the boundary logic, those tests tell you whether the direction holds. The prose above does not.

All the scripts must pass `shellcheck` with no finding. `tests/run_tests.sh` runs it first, over the hooks, the validator, and the runners themselves. So there is no separate command to remember after an edit. The scripts have a test suite under `tests/hooks/`. It uses `bats` (bats-core), not a custom harness. Run the whole suite with `tests/hooks/run_tests.sh`. Follow strict TDD when you change this logic. These scripts encode real decision functions, not incidental scripts. For example, the missing-reviews computation of `enforce-code-review.sh` has stated laws (monotonicity, invariance under order, and insensitivity to duplicates), and a test in `tests/hooks/enforce-code-review.bats` pins each one. So a behavior change starts with a new failed test.

## The `tests/plugins/` validator

`tests/plugins/validate-plugins.sh` is the only check of the Markdown and the JSON that are the product. Run it after each edit under `plugins/`:

```
tests/plugins/validate-plugins.sh          # check the repository
tests/plugins/run_tests.sh                 # check the validator itself (bats)
```

It prints one `path:line: message` per violation and exits with a nonzero status if there was one. Every check exists because the matching defect shipped before:

| Check | What shipped broken |
|-------|---------------------|
| an unquoted frontmatter scalar that holds ` #` | a YAML comment truncated four Racket descriptions in the middle of a sentence |
| a sibling file that the `SKILL.md` never names | thirteen `reference.md` files that nothing told the model to open |
| an unknown tool in `allowed-tools` or `tools` | `Task(...)` left in a skill after the harness renamed that tool to `Agent` |
| the two manifests disagree | see commit `665f550` |
| an agent with no `name`, `description`, `tools`, or `model`, a `model` outside `KNOWN_MODELS`, or a name that does not match its filename | the rule held only by convention |
| a skill with no `description` | a skill with no description can never trigger |
| a tool list written as an indented YAML block sequence | the entries never reached the tool check, so an unknown tool spelled that way passed |
| a frontmatter key that the harness does not read, or one written twice | `tools:` where the harness reads `allowed-tools:` grants no tools and says nothing; a repeated key took the last value with no error |
| a root with no `plugins/` directory, or with no skill and no agent | a mistyped path validated an empty set and printed `plugins: clean.` |
| an argument-scoped tool in the `tools` of an agent | the known-name check strips the argument off first, so the bare-names rule for agents held only in the prose of the meta plugin |

The frontmatter now has one reader. `read_markdown` publishes the keys, their raw values, their line numbers, the duplicates, and the body. No check parses a line of its own. With two parsers over one input, the truncation check disagreed with the loader about leading whitespace, and it reported a correctly quoted description as truncated whenever the description was indented.

Add a check as you add a hook behavior: first a failed test in `tests/plugins/validate-plugins.bats`, on a throwaway fixture tree and not on live repository content, then the check.

## Architecture and conventions specific to this repository

- **Two manifests state the description of each plugin.** Each plugin has its own `plugins/<name>/.claude-plugin/plugin.json`, and `.claude-plugin/marketplace.json` at the root of the repository repeats that description in its `plugins[]` entry. They drifted once already. See commit `665f550`. `tests/plugins/validate-plugins.sh` now compares them, and it also reports a plugin directory that is absent from the marketplace manifest. When the scope or the description of a plugin changes, update both files and run the validator.
- **An install copies the tree, into a directory named after the version.** `claude plugin install` writes a snapshot to `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`. A session loads that snapshot, never the working tree. So a content change that leaves `version` alone uses the same directory again, and nothing downstream can tell that the copy is stale. That occurred already. `development` got a whole agent (`efficiency-reviewer.md`) in commit `b27d40b` and a `model` field on every agent in `cfa0f0a`, all at version `0.1.0`. The installed copy had four agents where the tree had five. Increase `version` in `plugins/<name>/.claude-plugin/plugin.json` in the same change that edits the plugin. A new or changed skill or agent is a minor increase. Then reinstall as described under "Commands".
- **The difference between a skill and an agent, and how to write each one, is documented in this repository.** `plugins/meta/skills/write-skill/SKILL.md` and `plugins/meta/skills/write-agent/SKILL.md` are the canonical rules for the frontmatter fields, the tool scope, and the body structure of each new `SKILL.md` or agent file in this repository. Read those before you add or edit a skill or an agent. Do not infer the conventions from a single example, because some plugins are older than parts of that style guide.
- **The meta plugin states each authoring rule twice, and nothing keeps the two copies together.** `plugins/meta/skills/write-agent/SKILL.md` and `plugins/meta/agents/agent-writer.md` both hold the house rules for agent frontmatter. `write-skill/SKILL.md` and `skill-writer.md` hold the rules for skills in the same way. One copy is for direct use, and the other is for a subagent that gets the work. A rule changed in the skill but not in the matching agent leaves the delegated path with files that violate the rule that the skill just added. That occurred when the `model` field became mandatory. Update both.
- **Every agent names its model.** Each `plugins/*/agents/*.md` carries a `model` field: `haiku` for mechanical work, `sonnet` for judgement. None inherits the model of the caller. So the cost and the capability of an agent do not change with the model of the session. `tests/plugins/validate-plugins.sh` enforces this.
- **Skills in this repository are single files.** No plugin uses a `skills/<name>/references/`, `scripts/`, or `assets/` subdirectory. Everything is in one `SKILL.md`. The `reference.md` beside each `SKILL.md` of the `racket` plugin is the one exception. Those files are large lookup tables, not instructions. **A sibling file is reachable only if the body of the `SKILL.md` names it.** Nothing else tells the model to open it. Thirteen Racket skills once shipped a `reference.md` that no `SKILL.md` mentioned, and about 1,600 lines were stranded. The validator now requires the citation, rejects a citation that resolves to no file, and rejects a subdirectory inside a skill.
- **Quote every frontmatter value that holds a space and then a `#`.** YAML ends an unquoted scalar there. So a description that mentions a Racket `#:keyword` reaches the harness cut in half. It usually loses the `Use when...` clause that makes the skill triggerable at all, while the file on disk reads correctly. Four Racket skill descriptions shipped this way. The validator now rejects it.
- **The `local` and `global` plugins are parallel by design, not by accident.** `plugins/local/agents/settings-doctor.md` and `plugins/global/agents/settings-doctor.md` (and their `check-settings` skills) run mostly the same checks against different files (`.claude/settings.local.json` and `~/.claude/settings.json`). Where they overlap, their words are identical. Each one keeps what applies only in its own scope. `local` alone asks whether a rule duplicates one already granted at a higher level, and whether git ignores the file. `global` alone asks whether the hook scripts of a marketplace are wired into `hooks`. The two also describe the settings precedence differently, because the same file sits at the opposite ends of it. When you fix a defect in the check logic of one settings-doctor, check whether the other one has the same defect. No common file holds them together, so nothing keeps them in step automatically.
- **Commit messages follow a fixed template** (emoji, `[module] <new state, not action taken>` subject, Problem and Solution bullets, closing haiku). `plugins/git/skills/commit-message/SKILL.md` and the `git:commit-writer` agent codify it. Always call that skill (or the agent, when you delegate to a subagent) for every commit in this repository. Never write a commit message without the template, unless the user has explicitly said not to use the template. **The agent drafts only. It never commits.** It holds no tool that can call a subagent, so it cannot satisfy the prose-review gate of `confirm-git-commit-push.sh`. Its caller runs the reviewer and the commit. The subject and the bullets follow Simplified Technical English. The haiku is the one exception. The skill triggers on every explicit commit request on purpose, not only on the literal `/git:commit-message` command, so the format stays consistent with the existing log.
- **Prose follows Simplified Technical English (ASD-STE100).** Every response, code comment, commit message, planning document, and document in this repository obeys the condensed rules in `plugins/communication/skills/simplified-technical-english/SKILL.md`: the active voice, one instruction per sentence, no sentence over 20 words in a procedure or 25 in description, no "-ing" verb forms, "must" for a requirement, and the substitution table for software words. `hooks/enforce-prose-review.sh` enforces it for replies. The `communication:prose-reviewer` agent that it mandates applies the STE checks first, and the `communication:review-prose` skill applies the same checks on request.
- **`.org` files at the root of the repository are untracked on purpose.** `BadProseExamples.org` (the growing catalogue of prose failures that `review-prose/SKILL.md` and `prose-reviewer.md` each read at the start of a review) and `Review.org` are excluded by the global `~/.gitignore` of the user (`*.org`), not by the `.gitignore` of this repository (which is empty). If `BadProseExamples.org` is absent on a fresh checkout, that is expected. Both files tell the reviewer to fall back to the curated examples that they carry inline, and neither tells it to report the absence or to create the file. Do not try to force it into the repository. The two copies of that instruction drift as the copies of the meta plugin do. Change one, change the other.
